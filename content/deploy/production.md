# 生产部署与升级

## 入口与域名

正式部署应使用同源 HTTPS 入口，正确设置 `ISSUER_URL`、`AUTH_UI_URL`、`WEBAUTHN_RP_ID`、`WEBAUTHN_RP_ORIGINS` 和 `COOKIE_SECURE=true`。反向代理保留 `/api/`、`/oauth/`、`/.well-known/` 的转发；健康检查请求各模块的 `/api/v{n}/healthz`，前端不转发根路径 `/healthz`。启用 CSP 时，为 Turnstile 放行 `https://challenges.cloudflare.com` 的脚本与 iframe。

浏览器会访问下面几个入口，它们必须与账户页面共享同一 Cookie 主机范围：

| 入口 | 后端 | 说明 |
| --- | --- | --- |
| 账户前端 | Next.js `3288` | 将 `/api/v1/*`、`/oauth/*`、`/.well-known/*` 转发到 OAuth `8001`，将 `/api/v4/*` 的创作者操作转发到 `8004` |
| `NEXT_PUBLIC_ATHUB_API_URL` | ATHub `8005` | 小说库直连 `/api/v5/*`，不经过 Next.js |
| `NEXT_PUBLIC_CREATPLAT_API_URL` | 创作者平台 `8004` | 历史与贡献者查询直连 |
| `IMAGE_PUBLIC_URL` | 图床 `8002` | 图片地址 `/file/<ID>` 与上传接口 |

`NEXT_PUBLIC_*` 地址在前端构建时写入，变化后需要重建前端。反向代理不经回环地址连接后端时，把它的网段加入 `TRUSTED_PROXY_CIDRS`，否则登录限速等按来源地址生效的规则会把所有请求算作同一个来源。不要混用 `localhost` 和 `127.0.0.1`，Cookie 与 Passkey 的来源校验可能因此不一致。

## 聚合端口

后端另外监听 `8288`（`GATEWAY_HTTP_ADDR`），把四个模块合在一个端口上，反向代理只需要一个上游。请求按路径前缀交给对应模块，路径和查询参数保持不变：

| 路径前缀 | 模块 | 等同于直接访问 |
| --- | --- | --- |
| `/api/v1`、`/oauth`、`/.well-known` | OAuth | `8001` |
| `/api/v2`、`/file` | 图床 | `8002` |
| `/api/v4` | 创作者平台 | `8004` |
| `/api/v5` | ATHub | `8005` |

其他路径（包括根路径 `/healthz`）返回 404 `not_found`。请求进入的是各模块原有的处理链，来源校验、鉴权、限速和请求期限都与直接访问模块端口相同；ATHub 调用记录里的端口仍是 ATHub 自己的监听端口。原有四个端口照常监听，两种方式可以同时使用。

API 域名以 `8288` 为上游时，`NEXT_PUBLIC_ATHUB_API_URL`、`NEXT_PUBLIC_CREATPLAT_API_URL` 和 `IMAGE_PUBLIC_URL` 可以指向同一个域名，仍须与账户页面共享 Cookie 主机范围。

## 健康检查

四个模块的健康检查都在各自的版本前缀下，模块端口和聚合端口 `8288` 使用同一路径；根路径 `/healthz` 已取消：

| 路径 | 模块 | 模块端口 | 结果 |
| --- | --- | --- | --- |
| `/api/v1/healthz` | OAuth | `8001` | 正常返回 200；维护模式返回 433；账户库或维护状态读取失败返回 503 |
| `/api/v2/healthz` | 图床 | `8002` | 正常返回 200；图床库或文件目录不可用返回 503 |
| `/api/v4/healthz` | 创作者平台 | `8004` | 创作者库和账户库都可用时返回 200，否则返回 503 |
| `/api/v5/healthz` | ATHub | `8005` | 内容库不可用返回 503；不需要 Key，也不计入调用记录 |

例如 `http://127.0.0.1:8288/api/v4/healthz` 与 `http://127.0.0.1:8004/api/v4/healthz` 是同一个检查。监控按模块分别登记这四个地址；从旧版本升级时，把原来指向 `/healthz` 的监控地址和探活脚本改成上表的路径。

任一端口绑定失败时，程序会释放已绑定的端口并整体退出，不会只启动一部分模块。

## 密钥与备份

数据库迁移应作为独立发布步骤执行。加密密钥须与数据库一起备份、多实例保持一致；已有客户端只有哈希而没有加密副本时，需重置后才能在后台查看明文。不要在每次部署时重新生成加密密钥，也不要在生产使用 seed 的默认凭据。

- 备份范围包括四套数据库、`CLIENT_SECRET_ENCRYPTION_KEY`、`.env` 以及图床的文件目录 `IMAGE_LOCAL_ROOT`。
- 图床的对象文件与图床库不在同一个事务里，两者需要一起备份、一起恢复，见[图床失败恢复](/image/recovery)。

## 升级清单

1. 备份数据库、加密密钥和图片目录。
2. 停止旧版本后端。创作者库和图床的数据导入都要求先停写。
3. 执行有变化的数据库迁移，见[数据库与迁移](/deploy/database)。
4. 更新后端程序和前端构建，保留已有的 `.env`。
5. 启动后端与前端，检查四个模块的 `/api/v{n}/healthz`，再放开入口流量。

创作者库已经接收新的审核或修订之后，不能只把连接切回旧库来回退，见[创作者平台数据库](/creatplat/database)的回退限制。需要对外暂停服务时可以使用维护模式，见[站点开关与维护](/oauth/site)。

## 多实例

- 加密密钥在所有实例上保持一致。
- ATHub 的读缓存在进程内，多实例之间不会即时失效，由缓存有效期兜底，见 [ATHub 模块与数据库](/athub/module)。
- 会话不做缓存：每个实例对每次请求都直接核验账户库，退出登录和撤销在所有实例上立即生效。
- 图床的存储渠道配置与 IP 黑名单在每个进程内缓存 5 秒；在一个实例上修改后，其他实例最多延迟 5 秒生效。
