# 小说拆解与 API 上传规范

适用范围：将 TXT、EPUB 或其他可提取文字的小说整理为“小说元信息 → 卷 → 章节”，通过 ATHub API 导入。这里的“拆解”指结构提取与分章，不包含剧情分析、改写或生成原文中不存在的内容。

依据：[ATHub API 文档](/athub/overview)，核对日期：2026-11-17。接口字段、限制和响应以该文档为准；本规范补充拆解、数据整理与上传执行要求。

## 1. 执行流程

按以下顺序操作：

1. 确认原始文件、书名、来源平台及来源版本，保留原件。
2. 提取文字与目录，识别小说元信息、卷标题和章节边界。
3. 建立全书目录，确定稳定的卷序号、全书章节序号和卷章关联。
4. 检查漏章、重复、正文完整性和异常字符；未确认的边界先人工核对。
5. 查询或创建平台、作者、标签，取得真实 API ID。
6. 生成符合接口要求的 JSON，按实际 UTF-8 字节数分批。
7. 首批创建小说，保存服务端返回的 `novel.id`；其余批次用 `novelId` 续传。
8. 获取全书目录并读取正文，完成数量、顺序、关联及内容核对。

不得在目录仍有疑点时直接批量上传。上传端负责拆解和编码转换，服务端不会自动解析 TXT、EPUB、本地文件路径或压缩包。

## 2. 原始文件与文字提取

### 2.1 文件和过程记录

- 原始文件只读保留，拆解结果与原件分开保存。
- 临时脚本、拆解后的正文、上传 JSON、校验结果和上传进度统一放在工作区 `temp/novel-import/<任务标识>/`。
- 记录来源文件名、文件摘要、来源地址（如有）、编码、提取方式及使用的清理规则，便于复查。
- 本地的来源地址、摘要、路径、校验结果和进度均为过程信息，不得添加到 API 请求对象中。
- 不在文件、日志或版本库中保存真实 API Key。

### 2.2 提取要求

| 来源 | 处理要求 |
| --- | --- |
| TXT | 先识别并确认原始编码，正确解码后再处理；不得把乱码当作原文上传。 |
| EPUB | 按 spine 阅读顺序提取内容，结合导航目录确认卷章；目录只作辅助，不把目录页重复导入为正文。 |
| HTML | 提取阅读区的文字与段落，排除导航、脚本、样式等页面结构；不能把整页 HTML 当作正文。 |
| PDF、扫描件或 OCR 文本 | 先核对阅读顺序、分页断行、页眉页脚和识别错误；无法可靠还原时暂停对应内容的导入。 |

正文以纯文本上传。将 HTML 的段落和换行转换为文本换行，不保留用于页面排版的标签。对确有语义的文字、标点、空行和缩进应予保留，不做未经确认的润色、繁简转换或纠错。

插图和其他非文本资源不能通过章节接口上传。已经托管在图床上的插图，可在小说创建后用插图接口（API 文档第 12 节）按图片地址、SHA-256 和宽高关联到小说；该接口同样不接收图片二进制。对图片主导、含关键插图或无法可靠转为纯文本的内容，应记录未能导入的部分并人工处理，不能直接丢弃后声称内容完整。`coverUrl` 仅保存已有图片地址，不接收封面二进制。

遇到 NUL 字符、乱码或不明控制字符时，先定位原因并记录处理，不得静默删除可能属于正文的内容。输出的请求文件必须为 **UTF-8、无 BOM**。

## 3. 小说元信息整理

### 3.1 字段映射

以下字段用于首次上传的 `novel` 对象：

| 字段 | 规则 |
| --- | --- |
| `platformId` | 必填，引用已存在的来源平台 ID；不能使用平台名称或外站 ID 替代。 |
| `authorId` | 可选，作者必须属于 `platformId`；无法确认时使用 `null`，不猜测关联。不能与 `authorName` 同时提供。 |
| `authorName` | 可选，用作者姓名代替 `authorId`：在 `platformId` 下按姓名查找，同名时取 ID 最小的一位，找不到则新建。该平台可能存在同名的不同作者时，改用核对过的 `authorId`。 |
| `title` | 必填，使用原书名，去除首尾空白后不能为空。 |
| `summary` | 可选，有可靠来源则保留；没有则用 `null`，不生成简介冒充原简介。 |
| `coverUrl` | 可选，使用已知封面地址；没有则用 `null`，不能填写本机路径或图片数据。 |
| `status` | 只接受 `ONGOING`、`COMPLETED` 或 `ABANDONED`；确认完结后才能填 `COMPLETED`，确认作者已停止更新后才能填 `ABANDONED`，无法确认时按默认 `ONGOING` 处理并在本地记录待核实。 |
| `tagIds` | 可选，引用已存在的标签 ID，不得重复，最多 100 项；没有已确认标签时用 `[]`。 |
| `tagNames` | 可选，用标签名称代替或补充 `tagIds`，最多 100 项，每个名称最多 100 个字符；已存在的名称直接引用，不存在的会新建。名称区分大小写，提交前先与标签库核对写法，避免产生近似重复的标签。 |

缺少必要的平台归属或书名时，应先补齐信息。作者名、标签名只能通过 `authorName`、`tagNames` 提交；不接受 `author`、`tags`、`sourceUrl`、`filePath` 等额外字段。响应不回显这两个字段，只返回解析后的 `authorId` 和 `tagIds`，应保存下来用于后续核对。

### 3.2 取得平台、作者和标签 ID

1. 用 `GET /api/v5/platforms?limit=100&offset=0` 查询平台，核对名称和地址。缺少对应平台时，用 `POST /api/v5/platforms` 提交 `{"name":"来源平台","url":"https://example.com"}` 创建。
2. 用 `GET /api/v5/authors?platformId=<平台ID>&limit=100&offset=0` 查询该平台作者。确认不存在后，才用 `POST /api/v5/authors` 提交 `{"platformId":1,"name":"作者笔名"}` 创建。
3. 用 `GET /api/v5/tags?limit=100&offset=0` 查询标签。缺少所需标签时，用 `POST /api/v5/tags` 提交 `{"name":"奇幻"}` 创建。
4. 列表返回数组，每次将 `offset` 增加 `limit`，直到返回数量不足 `limit`，不能只检查第一页。
5. 保存查询或创建得到的真实 ID，再组装小说元信息。
6. 作者和标签在来源中名称明确、不会与同平台其他作者混淆时，可以跳过第 2、3 步的创建，直接在 `novel` 中提交 `authorName`、`tagNames`，由服务端在同一事务中查找或新建；首批失败时不会留下多余的作者或标签。

示例 ID 都是占位值，执行时必须替换。平台名称、作者姓名不唯一，重复 POST 会创建新记录，不会自动合并；同名作者需结合平台和来源身份核对。标签名称唯一且区分大小写，创建返回 `409` 时先重新查询核对。

创建小说前，也要按平台、作者分页查询 `/api/v5/novelinfo` 并核对现有作品。书名不唯一，同名只能作为核对线索，不能据此直接覆盖或自动合并。

## 4. 卷章拆解规则

### 4.1 边界识别

- 优先采用来源提供的有效阅读顺序和明确的卷章结构，再用标题特征辅助识别。
- TXT 中可将独占一行的“第一卷……”“第十二章……”“序章”“尾声”“番外”等视为候选标题；正文中出现相同词语不代表章节边界。
- 标题规则需结合整本书检查，不能用单条正则表达式无条件切割所有文本。
- 分卷标题写入卷的 `title`，章节标题写入章节的 `title`；结构标题不再作为同一章节的第一行重复导入。其后的正文保持原貌。
- 标题一经确认，应保留原始措辞与编号，不统一改写成新标题。API 会去除标题首尾空白。
- 序章、楔子、后记、尾声和番外若属于作品阅读内容，作为独立章节按阅读顺序保留。属于网站广告、重复目录或下载说明的内容，经确认后排除并记录。
- 拆分必须覆盖全部有效正文。首章之前、末章之后和卷标题之间的文字都需核对归属，不能静默遗漏。

特殊情况按以下规则处理：

| 情况 | 处理方式 |
| --- | --- |
| 原书没有分卷 | 不创建虚构卷，章节 `volumeOrder` 使用 `null`。 |
| 序章在首卷之前 | 保留为未分卷章节，`volumeOrder` 使用 `null`。 |
| 每卷从“第一章”重新编号 | 保留标题中的原编号，API 的章节 `order` 仍按全书顺序递增。 |
| 同名章节 | 根据来源位置分别保留，不能仅按标题去重。 |
| 疑似重复正文 | 核对来源目录和正文后决定，不仅凭标题或摘要自动删除。 |
| 只有卷标题、暂时没有章节 | API 允许空卷；记录原因，不能伪造占位正文。 |
| 章节正文为空或只有空白 | 不上传；查明是提取失败、目录误判还是来源缺失。 |
| 无标题的独立正文 | 人工确认其归属及标题，不能自动编造章节名称。 |
| 无法确认的分章边界 | 暂停对应部分，人工核对后再编号与上传。 |

### 4.2 编号与卷章关联

卷和章节分别维护一套编号：

- 卷的 `order`：从 `1` 开始，表示该卷在小说内的顺序。
- 章节的 `order`：从 `1` 开始，表示章节在**全书**的顺序，跨卷不重置。
- 新书首次导入建议各自连续编号；API 允许序号不连续。
- 序章、后记和番外也占用章节序号，不能使用 `0`、负数或字符串编号。
- 所有 ID 和序号均为 JSON 整数，范围为 `1` 至 `2147483647`，不能传 `"1"` 或小数。
- 本地目录确认后固定编号。分批、重试及修订时不得重新从 `1` 编号。

例如：

| 全书章节 `order` | `title` | 批量上传的 `volumeOrder` |
| --- | --- | --- |
| 1 | 序章 | `null` |
| 2 | 第一章 出发 | `1` |
| 3 | 第二章 相遇 | `1` |
| 4 | 第一章 远行 | `2` |
| 5 | 番外 重逢 | `null` |

其中卷 `order=1`、`order=2` 对应实际存在的两个卷。“第二卷第一章”的全书章节序号仍是 `4`。

**批量上传用 `volumeOrder` 引用卷序号；单章 `PUT /api/v5/content` 用 `volumeId` 引用数据库卷 ID。二者不能混用。**

### 4.3 正文完整性

- 保留章节内的段落顺序、标点、换行、首尾空白及缩进。
- 不把正文改成摘要，不省略“重复段落”，不擅自补全缺失内容。
- 不因换行或分页机械地产生新章节，不按固定字数切割原章节。
- 允许移除已经确认的页面噪声，但须在本地记录规则；不得把叙述内容误判为广告。
- 本地为每章保存 `order`、标题、卷序号和最终待上传正文的摘要，以便上传后比对。摘要等校验字段不能发送给 API。

## 5. JSON 格式与分批规则

### 5.1 通用要求

- 上传地址为 `POST https://api.albatextus.com/api/v5/upload`，不加查询参数或末尾 `/`。
- 使用个人 API Key：`Authorization: Bearer <API_KEY>`。旧全局密钥、OAuth access token、Cookie 和网站只读凭证不能用于上传。
- 请求头使用 `Content-Type: application/json; charset=utf-8`。
- 整个请求体是一个 UTF-8 JSON 对象；不是文件路径、顶层数组或 multipart 表单。
- 通过 JSON 序列化器生成请求，不手工拼接引号、反斜杠和换行。JSON 文件中的 `\n` 在解码后应为正文换行。
- 不提交 `id`、`createdAt`、`updatedAt` 或其他未声明字段；`novelId` 等接口明确定义的关联字段除外。
- 所有文本禁止 NUL 字符；标题不得为空，正文不得全为空白。

### 5.2 分批限制

每批必须同时满足：

| 限制项 | API 上限 |
| --- | --- |
| 整个 JSON 请求体 | 8 MiB，即 8,388,608 字节 |
| `volumes` 项数 | 200 |
| `chapters` 项数 | 1000 |

以**最终序列化后的 UTF-8 请求体字节数**判断大小，包含元信息、字段名、标点、转义和空白；不能用汉字数、字符串长度或原始 TXT 大小替代。

建议将普通批次控制在约 7 MiB 以内，留出组装余量；这是执行建议，不是 API 的额外限制。追加一章前先试算，超过任一上限就另起一批。即使只有几章，也可能超过字节上限。

每批章节引用的卷必须已在同一本小说中存在，或包含在本批 `volumes` 中。不要引用尚未上传的后续批次卷。没有分卷的书可省略 `volumes` 或使用 `[]`。

单章无法在 8 MiB 内装入合法请求时，停止该章上传并记录问题。当前接口不能分片拼接正文；不得用相同 `order` 依次上传多段，也不能为了绕过限制擅自把一章改成多章。

### 5.3 首批：创建小说

提供 `novel`，不提供 `novelId`。以下是结构示例，实际上传时须替换 ID、元信息和全部示例正文：

```json
{
  "novel": {
    "platformId": 1,
    "authorId": 2,
    "title": "示例小说",
    "summary": null,
    "coverUrl": null,
    "status": "ONGOING",
    "tagIds": []
  },
  "volumes": [
    {
      "order": 1,
      "title": "第一卷 启程"
    }
  ],
  "chapters": [
    {
      "order": 1,
      "volumeOrder": null,
      "title": "序章",
      "content": "序章第一段。\n\n序章第二段。"
    },
    {
      "order": 2,
      "volumeOrder": 1,
      "title": "第一章 出发",
      "content": "第一章正文。"
    }
  ]
}
```

成功返回 `201`。立即保存响应中的 **`novel.id`**，作为之后唯一的小说定位 ID。成功响应没有 `data` 外壳，不应读取 `data.novel.id`。

### 5.4 后续批次：续传

提供首批返回的 `novelId`，不再提供 `novel`：

```json
{
  "novelId": 10,
  "chapters": [
    {
      "order": 3,
      "volumeOrder": 1,
      "title": "第二章 相遇",
      "content": "第二章正文。"
    }
  ]
}
```

成功返回 `200`。以上 `novelId=10` 仅为示例，必须换成真实响应 ID。

续传至少包含一个卷或章节，只修改本批显式提交的内容，不清空其余卷章，也不修改小说元信息。已存在的卷可直接按 `volumeOrder` 引用，无需每批重复提交。

### 5.5 用 PowerShell 发送请求文件

将首批请求保存为 `temp/novel-import/<任务标识>/batch-001.json`。在工作区根目录执行，按实际任务目录替换示例路径，并事先在调用环境设置 `ATHUB_API_TOKEN`：

```powershell
curl.exe --silent --show-error --fail-with-body `
  --request POST 'https://api.albatextus.com/api/v5/upload' `
  --header "Authorization: Bearer $env:ATHUB_API_TOKEN" `
  --header 'Content-Type: application/json; charset=utf-8' `
  --data-binary '@temp/novel-import/example/batch-001.json' `
  --output 'temp/novel-import/example/batch-001.response.json' `
  --write-out '%{http_code}'
```

先确认 HTTP 状态码和响应，再生成或发送续传批次；此命令不自动提取并注入 `novelId`。不得使用 `-F file=@...`。响应文件可能包含作品信息，应按过程文件管理，不存入发布目录。

## 6. 上传进度、覆盖和失败恢复

### 6.1 上传记录

同一本书按批次顺序上传，避免并发修改相同序号。每批至少记录：

- 来源文件摘要、目录版本和真实 `novelId`。
- 批次编号、请求文件名、请求摘要和请求字节数。
- 本批卷序号、章节序号列表及预期章节数。
- 状态：未发送、结果待确认、成功或失败。
- HTTP 状态码、返回的卷章 ID、`chapterCount` 和必要的错误说明。

在请求前标记为“结果待确认”，收到并核对成功响应后再标记“成功”。未取得响应时不能自动记为失败或成功。日志中不得包含 Authorization 请求头或 API Key。

`chapterCount` 是**本批写入的章节数**，新增和覆盖都计数，不是全书章节总数。返回的 `volumes` 也仅包含本批显式写入的卷；仅被引用的旧卷不会额外返回。

### 6.2 覆盖语义

- 卷按 `(novelId, order)` 新增或覆盖，已有卷保留数据库 ID。
- 章节按 `(novelId, order)` 新增或覆盖，已有章节保留 ID，但标题、正文和卷关联会被本次数据替换。
- 覆盖时仍须提交完整章节对象。省略 `volumeOrder` 或传 `null` 会清除旧卷关联，不代表“保留原值”。
- 相同续传批次可重复发送，记录 ID 保持不变，但更新时间会更新；重试前应确认没有其他人的更新需要保留。
- 提交新序号会创建另一条记录，不会把旧章节自动移动到新位置。不要通过重新编号修复已有目录。
- 需要修改小说元信息时，使用 `PUT /api/v5/novelinfo?id=<小说ID>`，提交完整元信息；遗漏可空字段会清空，同时遗漏 `tagIds` 和 `tagNames` 会清空标签引用。

### 6.3 失败处理

| 情况 | 处理要求 |
| --- | --- |
| `202` | 账户角色开启了审核，本批尚未写入；记录 `review_id`，审核通过并查询确认后才能标记成功，不要重复提交。 |
| `400` | 核对字段、类型、重复序号、空正文、标签数量与名称长度及卷章关联，修正后重发。 |
| `401` | 核对个人 API Key 是否正确、有效及未被停用，不使用其他凭据替代。 |
| `403` | 账户角色没有该操作的权限；联系管理员确认权限，不要换用其他凭据重试。 |
| `404` | 核对路径和目标 ID，尤其是续传使用的 `novelId`。 |
| `405` | 核对 HTTP 方法；批量上传用 POST，单章上传用 PUT。 |
| `409` | 核对冲突资源；标签重名时先查询已有标签。 |
| `413` | 重新按最终 JSON 字节数分批。 |
| `415` | 使用 JSON Content-Type，并以整个 JSON 作为请求体。 |
| `500`、`503`、`504` 或网络中断 | 保存错误和请求信息，先确认提交结果；服务恢复后再决定重试。 |

每批是独立事务，批内写入失败会回滚该批；已经成功的其他批次不会因此撤销。跨批上传没有整书事务，进度须由上传端保存。

**首次创建没有按书名去重或幂等键。** 带 `novel` 的请求若超时、连接中断或未保存回执，不得自动重发。先按平台、作者分页查询小说候选，再核对元信息、目录和已上传正文；确认成功创建后恢复真实 `novelId`，改用续传。存在多个无法区分的候选时，先人工核对。

已有小说续传结果不明时，用目录及正文查询确认对应 `order` 的当前内容，再决定是否重发。不要为了恢复失败批次而删除整本小说。

## 7. 上传后验收

只有以下项目全部通过，才能标记“导入完成”：

- [ ] `GET /api/v5/novelinfo?id=<小说ID>` 返回正确的平台、作者、书名、简介、封面、状态及标签。
- [ ] `GET /api/v5/toc?novelId=<小说ID>` 返回的卷数、章节数与最终本地目录一致。
- [ ] 逐项比对卷和章节的 `order`、标题，确认没有漏章、多章或错误覆盖。
- [ ] 通过 `chapters[].volumeId` 对照 `volumes[].id` 核对分卷；`volumeId=null` 的章节也必须计入。
- [ ] 分页读取 `GET /api/v5/content?novelId=<小说ID>&limit=100&offset=0`，每次 `offset += 100`，直到返回数量不足 100。
- [ ] 将所有返回正文与本地最终待上传正文逐章比较，或对双方解码后的字符串使用相同 UTF-8 编码计算摘要比较；不要对整个 JSON 文件与正文计算结果交叉比较。
- [ ] 对首章、末章、每个换卷位置、序章和番外人工抽查，确认边界、段落及阅读顺序正确。
- [ ] 所有批次均有成功回执或已通过查询确认，没有待确认批次、未处理异常或未披露的内容缺失。

`/api/v5/toc` 一次返回全书目录，不接受分页参数，也不包含正文；正文验收须使用 `/api/v5/content`。目录顶层的 `wordCount` 是全书正文的非空白字符总数，可与本地统计对照作为辅助线索，不能替代逐章正文比较。分页验收期间应避免继续修改同一本书，防止读取到变化中的数据。

小说的 `updatedAt` 只反映元信息修改，不能作为卷章上传完成的依据。发生数量或内容差异时，只定位并修复对应记录，然后重新核对受影响部分。

## 8. 执行交付

每次实际导入结束后，提供以下结果：

1. 小说名称、真实 `novelId` 和来源文件标识。
2. 实际卷数、章节数、成功批次数，以及未分卷章节的处理情况。
3. 元信息、目录与正文校验结果。
4. 使用的清理规则、人工确认事项、缺失内容及尚未解决的问题（如有）。
5. 本地请求文件、回执和进度记录所在目录。

存在未解决的缺章、错误关联、正文差异或待确认提交时，应明确标记为“未完成”，不能只凭 HTTP 成功或章节计数声称全书导入完整。
