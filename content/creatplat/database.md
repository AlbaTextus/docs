# 独立数据库

创作者平台使用独立 PostgreSQL 数据库，由 `CREATPLAT_DATABASE_URL` 配置。它必须与 OAuth 的 `DATABASE_URL`、ATHub 的 `ATHUB_DATABASE_URL` 指向不同数据库。可以使用同一 PostgreSQL 实例中的不同数据库，也可以使用不同实例。

运行时不回退到 OAuth 库或内容库，不以不同 schema 代替独立数据库。应用启动只检查数据库是否独立以及表结构，不自动建库或修改表结构；建库与建表命令见[数据库](/deploy/database)。

## 数据归属

| 数据 | 存放位置 |
| --- | --- |
| 待审投稿、修订请求、提交时记下的改动、审核决定及执行结果 | 创作者库 `athub_reviews` |
| 贡献历史、修订差异、历史准备/确认状态 | 创作者库 `novel_revisions` |
| 用户、密码、session、外部 Key | OAuth 库 |
| 正式小说、章节、标签、插图关联、内容执行回执 | ATHub 库 |
| 角色权限、准入与调用记账 | 继续使用已有账户库适配器，归属尚未进一步调整 |

创作者库保存用户 UUID、作品 ID 和贡献者/审核者快照，不复制账户或登录秘密，不创建跨数据库外键。账户及角色检查仍由已有权威接口执行。

## 审核和历史的一致性

审核权限仍通过账户库检查，持有既有用户/角色策略锁，期间由创作者库保存提交或执行结果。两个数据库是独立事务，不宣称存在跨库原子事务。

审核决策在创作者库串行化，正式内容变更和执行回执仍在 ATHub 同一事务提交。内容已提交但审核结果落库失败时，重试复用同一审核 ID，通过原回执避免重复应用。提交者禁用、审核权限变化、禁止自审及操作权限限制继续生效。

历史使用创作者库的 pending → completed/failed 流程；内容提交后历史确认失败时保留待核对状态。用户删除和跨模块资料生命周期不再依赖跨库外键自动执行，相关业务如需新增行为应单独确认。
