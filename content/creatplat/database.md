# 独立数据库

创作者平台使用独立 PostgreSQL 数据库，由 `CREATPLAT_DATABASE_URL` 配置。它必须与 OAuth 的 `DATABASE_URL`、ATHub 的 `ATHUB_DATABASE_URL` 指向不同数据库。可以使用同一 PostgreSQL 实例中的不同数据库，也可以使用不同实例。

运行时不回退到 OAuth 库或内容库，不以不同 schema 代替独立数据库。应用启动只检查 schema 和旧数据迁移状态，不自动建库或修改表结构。

## 数据归属

| 数据 | 存放位置 |
| --- | --- |
| 待审投稿、修订请求、提交时记下的改动、审核决定及执行结果 | 创作者库 `athub_reviews` |
| 贡献历史、修订差异、历史准备/确认状态 | 创作者库 `novel_revisions` |
| 旧数据导入来源、记录数、逐字段摘要及完成时间 | 创作者库 `creator_migration_state` |
| 用户、密码、session、外部 Key | OAuth 库 |
| 正式小说、章节、标签、插图关联、内容执行回执 | ATHub 库 |
| 角色权限、准入与调用记账 | 继续使用已有账户库适配器，归属尚未进一步调整 |

创作者库保存用户 UUID、作品 ID 和贡献者/审核者快照，不复制账户或登录秘密，不创建跨数据库外键。账户及角色检查仍由已有权威接口执行。

## 首次建立

1. 由数据库管理员建立独立库及运行账号，并将连接写入服务端 `.env` 的 `CREATPLAT_DATABASE_URL`。
2. 如果目标连接账号拥有 `CREATEDB` 权限，可以运行 `npm run db:creatplat:create`。该命令使用目标连接账号登录 PostgreSQL 维护库，只创建配置中指定且尚不存在的数据库；不会替换已有数据库。
3. 运行 `npm run db:creatplat:validate`，再运行 `npm run db:creatplat:deploy`，应用本模块独立迁移链。
4. 现有安装升级时，停下全部 ATN 后端写入，包括旧版本程序；随后运行 `npm run db:creatplat:import`。
5. 导入通过后启动新版本。全新安装且账户库没有旧审核/历史数据时，无需导入旧数据。

Prisma 命令和迁移工具都从根目录运行，读取根 `.env`。账号、密码、服务器地址均来自环境配置，不能将实际连接提交到仓库。

Docker Compose 新增 `creatplat-postgres` 与独立 volume。配置 `CREATPLAT_POSTGRES_PASSWORD`、`CREATPLAT_COMPOSE_DATABASE_URL`；后者必须使用容器网络内的 `creatplat-postgres` 主机及对应账号/数据库。宿主机执行 Prisma 时，`CREATPLAT_DATABASE_URL` 则使用实际宿主访问地址，默认映射端口为 `5434`。数据库容器健康只表示 PostgreSQL 可连接，不表示迁移已完成。

## 后续迁移

建库之后的结构变更同样通过 `prisma/creatplat/` 的迁移链发布，应用不会自行修改表结构。升级到带有新迁移的版本时，在启动新版本之前运行 `npm run db:creatplat:deploy`；表结构缺少新版本需要的列时启动检查不通过，服务拒绝启动。升级的完整顺序见[数据库与迁移](/deploy/database)。

| 迁移 | 说明 |
| --- | --- |
| `20261119000000_review_baseline` | 为 `athub_reviews` 增加可空的 JSONB 列 `baseline`，保存一项需审核的提交在预演时实际改动了哪些内容及其原值。通过审核时据此只写入提交改动的内容，并在这些内容已被改过时拒绝写入，见[投稿、编辑与审核](/creatplat/workflow)。这一列只在服务端内部使用，不出现在审核接口返回的记录里。迁移只增加这一列，不回填已有记录：升级前已在排队的提交该列为空，通过时仍整份写入。 |

## 旧数据迁移与核对

迁移工具读取 `DATABASE_URL` 中原有的 `athub_reviews` 和 `novel_revisions`，写入 `CREATPLAT_DATABASE_URL`：

- 保留主键、用户/审核者标识、JSON 内容、原审核状态、原历史状态和时间；不补造旧贡献者或正文差异。
- 锁定源审核/历史表以阻止并发变更；锁定目标表，目标非空且没有有效导入标记时拒绝覆盖。
- 流式读取、参数化写入，JSON 以原始文本转存，避免大整数经浮点转换丢失精度。
- 对源与目标按稳定 ID 排序，计算整行 JSON 的 SHA-256，并比对实际记录数；全部一致后，将数据和导入标记在一个目标事务中提交。创作者库后来增加的 `baseline` 列旧表没有：导入不写入这一列，摘要也不计入它，此前的导入标记不受影响。
- 中途失败回滚目标事务，源数据不变；重复运行相同已导入来源时不重复插入。来源变化时拒绝自动覆盖。
- 导入不执行内容变更，不重复批准历史审核，也不改写 ATHub 的执行回执。

启动时会核对旧来源是否已导入。已有旧数据却缺少导入标记、或旧来源在导入后行数发生变化时，拒绝启动，避免静默展示空历史或持续产生两份数据。

启动时只比对来源库身份和两张旧表的行数，不阻塞业务监听器。逐行核对在监听器就绪后于后台执行，期限为 `CREATPLAT_MIGRATION_CHECK_TIMEOUT`，默认 `10m`，必须为正时长；历史量较大时可按实际核对耗时调整。后台核对发现旧来源被改动时，服务会停止并以错误退出；核对超时或连接失败只记录错误日志，不停止服务。

旧账户库中的两张表及其历史迁移暂时保留，不删除，不再作为新版本的创作业务写入目标。导入后不得继续运行仍向旧表写入的版本。

## 审核和历史的一致性

审核权限仍通过账户库检查，持有既有用户/角色策略锁，期间由创作者库保存提交或执行结果。两个数据库是独立事务，不宣称存在跨库原子事务。

审核决策在创作者库串行化，正式内容变更和执行回执仍在 ATHub 同一事务提交。内容已提交但审核结果落库失败时，重试复用同一审核 ID，通过原回执避免重复应用。提交者禁用、审核权限变化、禁止自审及操作权限限制继续生效。

历史使用创作者库的 pending → completed/failed 流程；内容提交后历史确认失败时保留待核对状态。用户删除和跨模块资料生命周期不再依赖跨库外键自动执行，相关业务如需新增行为应单独确认。

## 回退限制

新版本还没有产生新写入时，可以停止服务后恢复原配置与旧版本。新库已经接收审核或修订后，不能只切回旧连接：需要先停写、核对差异并准备反向同步，否则会丢失切换后的创作数据。

## 验证

集成测试使用 `OAUTH_TEST_DATABASE_URL` 与 `CREATPLAT_TEST_DATABASE_URL`，在两个不同数据库中创建随机命名的临时 schema，结束后清理。测试覆盖数据导入核对、重复导入保护、旧写入检测、独立库存储、账户禁用和重复审核执行保护。
